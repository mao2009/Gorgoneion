# v0.1 vertical slice (prototype)

This is a **dry-run-only** prototype. It **does not** contact, modify, or configure external systems and makes no claim to protect production workloads.

## Run

Requires .NET SDK 8. Build both projects with `dotnet build Gorgoneion.sln -c Release`. The input subset is described in [schemas/eve-subset.schema.json](../schemas/eve-subset.schema.json), which is documentation only, not a runtime validation engine.

```sh
dotnet run --project src/Gorgoneion.Cli -- evaluate --policy examples/policy.example.json --authorization examples/authorization.example.json --input examples/eve.example.jsonl --audit ./gorgoneion-audit.jsonl
dotnet run --project tests/Gorgoneion.SmokeTests
```

Optionally append `--strategies examples/strategies.example.json` after the `--audit` output argument to select a versioned, code-allowlisted, dry-run-only capability. Unknown or ambiguous strategies fail closed. See [strategy catalog](strategy-catalog.md).

Reads Suricata-style newline-delimited EVE JSON, a local allowlist of **destination** IP addresses, and an independently supplied **versioned authorization snapshot**. Plans are denied unless a uniquely enrolled asset and a matching, unexpired approval both exist. Missing authorization file is a CLI error. The checked-in example uses documentation-only addresses and an intentionally distant date to support repeatable demo runs; it is NOT a production enrollment or genuine permission. Proposed actions use only the hardcoded `firewall.mock` adapter and are never executed.

## Assumptions / limitations

- The prototype maps alert severity 1..4 to a configurable upper threshold (lower number = higher priority in Suricata conventions).
- The authorized target registry is an explicit local policy file, **not** proof that the operator owns the endpoint. External enforcement must add strong asset attestation and identity/approval.
- Source IPs do not establish attacker identity. This is a simulated defensive recommendation only.
- No remote APIs, sockets, FW rule changes or OS privileges are used.
- A privacy-minimal per-run audit JSONL file is now mandatory, with an unkeyed SHA-256 hash chain and built-in verification (`verify-audit --input FILE`). It records no raw addresses or signatures, but does contain decision/action metadata. The file must be new, not an existing file. A hash chain does **not** prevent complete tail truncation, substitution of a whole ledger, or attacker rewriting it; immutable remote anchoring, timestamps/signatures and archival/retention are still missing.
- No signed evidence store, digital signatures, streaming backpressure, anomaly correlation, CIDR ranges or strategy registry yet.
- The authorization snapshot is a **local JSON assertion**, not signed or independently authenticated. A real execution engine would require verified ownership, identity and reauthorization before acting.
- Invalid lines produce denied outputs. CLI returns a nonzero exit status for invalid policy/file errors.

## Development priorities

1. Audit existing OSS workflow and policy engines before creating custom equivalents.
2. Split CLI into library and adapter interfaces only when real integration demands it.
3. Add schema, large-input limits, streaming and structured diagnostic controls before production deployments.
4. Add formal testing and SBOM after the license decision.

## Security baseline

The sample addresses are RFC 5737 documentation-only networks. Never substitute a production address without explicit authorization and appropriate controls.
